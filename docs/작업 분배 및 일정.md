## 1. 원칙

- **계약 우선**: 백엔드는 D3까지 API 명세의 예시 JSON을 그대로 돌려주는 Swagger 스텁을 띄운다. 프론트는 그 스텁으로 화면을 만든다.
- **흐름 단위 분할**: 한 사람이 한 사용자 흐름을 처음부터 끝까지 맡는다.
- **접점 최소화**: 담당자끼리는 테이블 하나나 메서드 하나로만 맞물린다(4장).
- **문서가 기준**: 구현 기준은 개발 문서 v1.4이다. PRD와 다르면 개발 문서를 따른다. 남은 PRD 문구는 TRD 16-1에 정리돼 있다.
- **AI 사용**: 각자 원하는 AI 도구를 써도 된다. 레포의 `AGENTS.md`와 `docs/`가 기준이고, 명세에 없는 필드나 API는 만들지 않는다. 자세한 건 레포의 `CONTRIBUTING.md` 7장.
- **작업 관리**: API·화면 하나가 GitHub 이슈 하나다. 진행 상황은 GitHub Projects 보드로 보고, 기획 문서와 회의록은 노션에 둔다.

## 3. 문구 확정 일정

기획 질문("화면별 문구 확정은 언제까지?")에 대한 답이다. 문구는 어디에 들어가느냐에 따라 마감이 다르다.

| 구분 | 내용 | 마감 | 이유 |
| --- | --- | --- | --- |
| 서버가 내려주는 문구 | 동의 약관 본문(TERMS-01), 위기 안내 5.5와 연락처, 소진 안내 5.4, 에러 메시지(API 명세 4장 표), 돌봄 지원 추천 이유 템플릿 | **D4 (11/7)** | 백엔드 시드·상수로 들어가 D4부터 구현한다. 초안은 AI 명세 5장·API 명세 4장에 있으니 고칠 부분만 표시하면 된다 |
| 화면 UI 문구 | 버튼, 화면 안내, 빈 상태, 로딩, 확인 팝업 | **D7 (11/10)** | 프론트가 D8~D10에 실제 API를 연결하면서 넣는다. 그 전에는 와이어프레임 문구로 만든다 |
| 최종 수정 | 전체 | **D10 (11/13)** | 이후에는 오타만 고친다 |

화면 문구는 노션에 화면 번호(0.1, 2.2 …)별 표로 정리해 주면 프론트가 그대로 옮긴다.

## 6. 운영 규칙

- **매일 10분 공유**: 시간을 정해 고정한다. 어제 한 것보다 막힌 것과 상대에게 필요한 것만 말한다. 진행 상황은 GitHub Projects 보드로 본다.
- **흐름**: 이슈 → 브랜치 `{type}/{이슈번호}-{설명}` → PR(`Closes #번호`) → CI·리뷰 → Squash Merge
- **커밋·PR 제목**: `feat(share): 공유 승인 시 토큰 발급 (SHARE-03)` 형식. PR 제목은 CI가 검사한다
- **리뷰 짝**: 백엔드 A→B, B→C, C→A, 프론트 A↔B. 승인 1명 후 Squash Merge
- **API 하나가 끝났다는 기준**: Swagger가 API 명세와 같고, 규칙이 있는 곳은 단위 테스트가 있고, dev 서버에 배포됐다.
- **스키마 변경**: Flyway 파일은 누구나 새로 추가한다. 머지된 파일은 고치지 않는다. ERD 문서는 백엔드 A가 같이 고친다.
- **API 변경**: Swagger를 먼저 고치고, 맞붙는 프론트에 알린 다음 구현한다.
- **D7 작업량 점검**: 밀린 사람이 있으면 여유 있는 사람에게 옮긴다. 백엔드에서 옮기기 쉬운 것은 HOME-01과 INVITE-04~06(받은 초대)이다. 다른 코드와 얽힌 곳이 적다.
- **시연 안전장치**: 시연 일기는 평가셋에 넣어 mock으로 바꿔도 같은 결과가 나오게 한다. 녹음이 실패하면 텍스트 입력으로 진행한다. 시연 기기와 브라우저는 D12 전에 정해 둔다.
