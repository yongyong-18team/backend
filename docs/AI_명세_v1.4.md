### 1-2. 원칙
1. 일기에 적힌 내용만 다룬다. 없는 사실, 복약, 대처 방법은 만들지 않는다.
2. 진단, 원인 단정, 치료 조언, 상담을 하지 않는다.
3. LLM은 라벨과 문장만 만든다. 위기 분기, 설명서 반영, 제도 자격 판단은 서버가 한다.
4. 보호자 본인의 상태는 돌봄 정보(items)에 섞지 않는다. 소진·위기 신호로만 따로 다룬다.
5. 출력은 항상 JSON이다. 검증을 통과하지 못한 값은 버린다.

## 2. 공통 처리

### 2-1. 모델 설정

| 항목 | AI-01 | AI-03 | AI-04 | AI-05 |
|---|---|---|---|---|
| temperature | 0.2 | 0.3 | 0.3 | 0.3 |
| 최대 출력 토큰 | 1500 | 300 | 150 | 300 |
| 출력 형식 | JSON (스키마 강제 기능이 있으면 사용) | 동일 | 동일 | 동일 |
| 타임아웃 | 15초 | 10초 | 10초 | 10초 |
| 재시도 | 즉시 실패 시 1회 | 없음 | 없음 | 없음 |
| 전체 상한 | 25초 | - | - | - |

- 즉시 실패: LLM API 5xx 응답, JSON 파싱 실패
- 타임아웃은 재시도하지 않는다. 다시 기다리면 NFR-02(p95 15초, 최대 25초)를 넘기 때문이다.
- 공급자를 정한 뒤 평가셋으로 실제 지연 시간을 재서 다시 조정한다.

### 2-2. 전처리: 마스킹
1. **이름 치환**: 대상자 이름(care_subject.name)을 `대상자`로 바꾼다. 조사가 붙은 경우 포함(`민지가` → `대상자가`). 이름은 2자 이상(ERD CHECK)
2. **전화번호 제거**: 아래 패턴을 `[연락처]`로
   - `01[016789]-?\d{3,4}-?\d{4}`
   - `0\d{1,2}-?\d{3,4}-?\d{4}`
3. **비상 연락처 제외**: care_subject.emergency_contact는 LLM에 보내지 않는다.

다른 사람의 이름(활동지원사, 가족)은 MVP에서 처리하지 않는다. 가상 데이터만 쓰므로 해커톤 범위에서 허용한다.

### 2-3. 후처리: 공통 검증
1. JSON 파싱 실패 시 재시도 1회(2-1), 그래도 실패하면 작업별 실패 처리(7장)
2. enum 값이 목록에 없으면 해당 항목을 버린다.
3. 길이 제한을 넘는 문자열은 자르지 않고 버린다.
4. 저장 전에 `대상자`를 원래 이름으로 되돌린다.

### 2-4. 근거 문장 검증 (AI-01)
- evidenceQuote가 **마스킹된 원문**에 포함되는지 확인한다.
- 비교 전 양쪽 정규화: 공백 제거, 문장부호 `.,!?~…'"“”‘’` 제거
- 포함되지 않으면 그 항목을 버린다.

### 2-5. 버전 관리
- 프롬프트 파일: `src/main/resources/prompts/`
- 파일명 `{작업}_v{n}.txt`. 내용을 바꾸면 새 번호 파일을 만들고 기존 파일은 고치지 않는다.
- 사용 버전은 설정값(`ai.prompt.analyze-diary=v1`)으로 지정하고 ai_analysis.prompt_version에 기록한다.
- 키워드만으로 위기를 판정한 경우(LLM 실패) prompt_version은 `keyword-only`
- 버전을 올리기 전에 평가셋(6장)으로 기존 버전과 비교한다.

### 2-6. 로깅
LLM 요청·응답 본문은 남기지 않는다. 작업 ID, 공급자, 모델, 프롬프트 버전, 지연 시간, 성공 여부, 버려진 항목 수만 남긴다.

### 3-2. 프롬프트 (analyze_diary_v1)

**System**
```
너는 발달장애인 돌봄 기록을 정리하는 도우미다. 보호자가 쓴 일기에서 돌봄에 필요한 정보를 뽑아 JSON 하나로 돌려준다.

[기본 규칙]
1. 일기에 적힌 내용만 쓴다. 추측하거나 지어내지 않는다. 일기에 없는 복약, 의학 정보, 대처 방법은 만들지 않는다.
2. 진단, 원인 단정, 치료 조언, 상담을 하지 않는다.
3. "대상자"는 돌봄을 받는 사람이다. 일기를 쓴 사람은 보호자다.
4. 모든 items의 evidenceQuote에는 일기 원문의 일부를 글자 그대로 복사한다. 고쳐 쓰지 않는다.
5. 보호자 자신의 감정, 건강, 피로는 items에 넣지 않는다. burnoutSignal로만 표시한다.
6. 정보가 없으면 null이나 빈 배열로 둔다. 빈칸을 채우려고 만들어 내지 않는다.

[safetyLevel]
- CRISIS: 보호자가 다음을 드러낼 때
  - 자살이나 자해에 대한 생각, 계획
  - 대상자나 다른 사람을 해치려는 생각
  - 대상자와 함께 죽겠다는 생각
  - 지금 누군가 크게 다쳐 즉시 도움이 필요한 상황
- NORMAL: 그 외 전부.
  - "힘들어 죽겠다", "배고파 죽겠다" 같은 관용 표현은 NORMAL이다.
  - 대상자의 자해, 공격, 파손 같은 도전 행동을 기록한 것은 NORMAL이다. 이것은 items의 BEHAVIOR로 기록한다.
- CRISIS면 empathy는 null, items는 []로 둔다.

[empathy]
보호자의 하루를 알아주는 1~2문장, 60자 이내.
조언, 평가, 해결책, "힘내세요" 같은 당부를 넣지 않는다.

[items.category]
ROUTINE: 하루 일과, 생활 습관
CONDITION: 대상자의 수면, 컨디션
MEAL: 식사, 식습관
MEDICATION: 복약. 일기에 적힌 그대로만 쓴다
COMMUNICATION: 의사 표현 방식, 알아듣는 방식
BEHAVIOR: 도전 행동
TRIGGER: 도전 행동이 일어나기 직전의 상황이나 자극
PREFERENCE: 좋아하는 것, 안정되는 것
AVERSION: 싫어하는 것, 피해야 할 자극
RESPONSE: 보호자가 한 대처와 그 결과

[items 필드]
- label: BEHAVIOR일 때만 아래 목록 중 하나. 그 외 category는 null
  소리 지름 / 자해 행동 / 타인 공격 / 물건 파손 / 뛰쳐나감 / 반복 행동 / 수면 문제 / 식사 거부 / 기타 행동
- content: 돌봄하는 사람이 읽을 한 문장, 80자 이내. 주어 "대상자"는 생략해도 된다
- timeSlot: 일기에 시간대가 드러날 때만. MORNING(5~12시) / AFTERNOON(12~18시) / EVENING(18~22시) / NIGHT(22~5시). 모르면 null
- durationMin: 지속 시간이 적혀 있을 때만, 분 단위 정수. 모르면 null
- episodeNo: 한 사건에 속한 TRIGGER, BEHAVIOR, RESPONSE에 같은 번호(1부터). 사건과 무관하면 null

[burnoutSignal]
보호자가 자신의 지침, 한계, 계속되는 수면 부족, 버티기 어렵다는 마음을 드러내면 true. 아니면 false.
진단하거나 이유를 해석하지 않는다.

[출력]
지정된 JSON 하나만 출력한다. 설명 문장을 붙이지 않는다.
```


돌봄 공백 후보(gapCandidate)는 P1에서 프롬프트 v2로 추가한다. PRD 5.1이 MVP를 "보호자 직접 입력 기반"으로 정했기 때문이다.

|---|---|

| MEAL, MEDICATION | MEDICATION 복약 정보·주의사항 |
| COMMUNICATION | COMMUNICATION 의사소통 방법 |

### 3-4. 서버 후처리 순서
1. 위기 키워드 검사(3-5)는 LLM 호출 **전에** 원문으로 한다. 결과를 보관한다.
2. LLM 응답을 파싱하고 스키마를 검증한다.
3. 키워드가 적중했거나 `safetyLevel=CRISIS`면 CRISIS로 처리한다. empathy, items는 저장하지 않는다.
4. **LLM 호출이 실패했는데 키워드가 적중한 경우**에도 CRISIS로 저장한다. 이때 ai_analysis는 `raw_json = NULL`, `model_name = NULL`, `prompt_version = 'keyword-only'`
5. LLM 호출이 실패하고 키워드도 적중하지 않으면 FAILED (7장)
6. NORMAL이면 items를 하나씩 검증한다(enum, 길이, 근거 문장). 실패한 항목만 버린다.
7. BEHAVIOR가 아닌 항목의 label은 null로 바꾼다. 목록에 없는 label은 `기타 행동`으로 바꾼다.
8. 이름을 되돌리고 저장한다(순서는 TRD 8-3).
9. 남은 items가 0개면 `result=NO_ITEMS`

### 3-5. 위기 키워드 사전 (서버)
- 파일: `crisis_keywords_v1.txt`, 한 줄에 하나
- 비교: 원문과 사전 항목 모두 공백을 제거하고 포함 여부 확인
- 범위: **보호자 본인의 1인칭 표현**만
  - 자살·자해 의도: 예) "죽고 싶", "사라지고 싶", "끝내고 싶"
  - 동반 의도: 예) "같이 죽", "데리고 죽"
  - 타해 의도: 보호자가 대상자나 타인을 해치겠다는 표현
- 넣지 않는 것
  - "죽겠다" 단독: 관용 표현 오탐이 너무 많음
  - "자해", "때렸다" 단독: 대상자의 도전 행동 기록과 구분 안 됨
- 전체 목록은 기획과 함께 작성하고, 평가셋 혼동 사례로 오탐을 확인한 뒤 확정한다.

**오탐을 허용하는 이유**: 위기를 놓치면 위기인 보호자에게 공감 문장과 "항목을 승인하세요" 화면이 나간다. 오탐이면 괜찮은 보호자에게 안전 안내가 한 번 뜨고 그 일기의 추출이 빠진다. 앞쪽 피해가 훨씬 크다. 대신 키워드 범위를 좁히고 오탐률을 따로 측정한다(6-3).

### 3-6. 소진 누적 판정 (서버)
```
burnoutSignal=true면
  wellbeing_signal(user, BURNOUT, 오늘 날짜) 저장 (같은 날 이미 있으면 무시)

다음을 모두 만족하면 burnoutNotice=true
  - 최근 14일(오늘 포함) 동안 BURNOUT 신호가 기록된 날짜가 3일 이상
  - users.last_burnout_notice_at이 NULL이거나 14일 이전
이때 last_burnout_notice_at = now()
```
- 날짜는 KST 기준
- CRISIS 신호는 이 계산에 넣지 않는다.

## 4. AI-03 ~ AI-05 (P1)

MVP에서는 호출하지 않는다. P1에서 켤 때 아래 명세를 따른다. 꺼져 있을 때의 동작은 각 항목의 "MVP" 줄에 적었다.

### 4-1. AI-03 공유 문서 상단 요약 (화면 4.2)

**MVP**: 호출하지 않는다. SHARE-02의 `summaryLines`는 빈 배열이다.

**입력**: 문서 유형, 공개하기로 한 승인 항목 목록(마스킹). 수신자 유형은 없다(PRD 4.1).

**System (summarize_share_v1)**
```
너는 돌봄 인수인계 문서의 맨 위에 들어갈 요약을 쓴다.

규칙
1. 아래 항목에 있는 내용만 쓴다. 새로운 사실, 복약 지시, 의학 정보, 대처 방법을 만들지 않는다.
2. 처음 돌보는 사람이 가장 먼저 알아야 할 것을 고른다. 절대 금지, 건강 위험, 행동 특성 및 위기 대응을 우선한다.
3. 최대 3문장, 문장당 50자 이내. 존댓말로 쓴다.
4. 원인을 단정하지 않는다.
5. JSON 하나만 출력한다.
```

**출력**: `{ "summaryLines": ["큰 소리나 공사 소음에 불안해할 수 있어요.", "불안해하면 차에서 트로트를 틀어주면 진정되는 편이에요."] }`

**검증**
- 요약에 나온 숫자(시간, 횟수, 용량)가 입력 항목에 없으면 요약 전체를 버린다. 복약 용량이 바뀌는 사고를 막기 위해서다.
- 문장 수·길이를 넘으면 요약 전체를 버린다.
- 요약이 버려져도 공유는 진행한다(`summaryLines: []`).

### 4-2. AI-04 자원 추천 이유 (화면 5.2)

**MVP**: 템플릿 문장을 쓴다. 제도는 `"{단기|장기} 돌봄과 관련된 제도예요."`, 시설은 `"{구}에 있는 {시설 유형}이에요."`

**입력**: 돌봄 유형(단기·장기), 자원 이름·종류·구, 매칭된 규칙 이름

**System (explain_recommendation_v1)**
```
너는 돌봄 자원을 추천하는 이유를 한 문장으로 쓴다.

규칙
1. 입력에 있는 사실만 쓴다.
2. 이용 가능 여부, 선정 여부, 정원을 단정하지 않는다. "이용할 수 있어요", "바로 신청됩니다" 같은 표현을 쓰지 않는다.
3. "관련된 제도예요", "알아볼 수 있는 곳이에요"처럼 안내하는 말투로 쓴다.
4. 60자 이내, 존댓말.
5. JSON 하나만 출력한다.
```

**출력**: `{ "reasonText": "잠시 돌봄을 맡길 곳이 필요할 때 알아볼 수 있는 제도예요." }`

**검증**: 금지 표현(`이용 가능`, `이용할 수 있`, `바로`, `보장`, `확정`, `선정`)이 있으면 MVP 템플릿으로 대체한다.

### 4-3. AI-05 주간 리포트 요약 문장 (화면 2.5)

**MVP**: 주간 리포트 자체가 P1이다.

**입력**: 서버가 집계한 값만 보낸다. 일기 원문, 근거 문장, 보호자 상태는 보내지 않는다.
```json
{
  "periodStart": "2026-10-28",
  "periodEnd": "2026-11-03",
  "recordCount": 5,
  "behaviorCount": 7,
  "dailyTrend": [ { "date": "2026-10-28", "behaviorCount": 2 }, { "date": "2026-10-29", "behaviorCount": 0 } ],
  "repeatedBehaviors": [ { "label": "소리 지름", "count": 3 } ],
  "timePattern": [ { "timeSlot": "AFTERNOON", "count": 3 } ],
  "keyChanges": [ { "section": "PREFERENCE", "content": "담요를 덮어주면 안정됨" } ]
}
```

**System (summarize_weekly_v1)**
```
너는 최근 7일 동안 기록된 돌봄 관찰을 2~3문장으로 정리한다.

규칙
1. 입력된 수치와 항목만 쓴다. 입력에 없는 행동, 숫자, 대처 방법을 만들지 않는다.
2. 관찰된 경향으로만 쓴다. "~하는 경우가 많았어요", "~가 기록됐어요"처럼 쓴다.
3. 원인을 단정하지 않는다. "때문에", "원인은" 같은 표현을 쓰지 않는다.
4. 진단, 치료 조언, 평가를 하지 않는다.
5. 일기 수(recordCount)와 행동 횟수(behaviorCount)를 섞어 쓰지 않는다.
6. 문장당 60자 이내, 존댓말.
7. JSON 하나만 출력한다.
```

**출력**: `{ "summaryLines": ["최근 7일 동안 소리를 지르는 행동이 3번 기록됐어요.", "주로 오후에 있었고, 담요를 덮어주면 안정된다는 내용이 새로 추가됐어요."] }`

**검증**
- 요약에 나온 숫자가 입력 값에 없으면 요약 전체를 버린다.
- 금지 표현(`때문`, `원인`, `진단`, `치료`)이 있으면 요약 전체를 버린다.
- 실패하면 `summaryLines: []`. 화면은 집계 수치만 보여준다.
- recordCount가 3 미만이면 호출하지 않는다.
