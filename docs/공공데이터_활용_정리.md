# 공공데이터 활용 정리

발표 자료, 기획안 보완, 이후 개발에 같이 쓰려고 정리한 문서다. 2026-11-14에 작성했다.

- 현재 상태(1~3장)는 레포의 코드와 시드, 이슈 #29·#30·#31, PR #73에서 확인한 사실만 적었다.
- 후보 데이터(4장)는 2026-11-14에 공공데이터포털 상세 페이지로 확인했다. API를 직접 호출해 본 것은 #29에 기록된 두 건뿐이다.
- `[확인 필요]`는 아직 확인하지 못해 발표나 기획에 그대로 쓰면 안 되는 항목이다.

## 1. 요약

용인시 장애인복지시설 53곳과 공식 사업안내 기반 지원제도 5개를 DB에 넣어 두었다. 보호자가 단기·장기와 지역을 고르면, 대상자 나이에 맞는 제도와 그 제도에 연결된 유형의 시설을 같은 구부터 보여준다.

공공데이터 API를 실시간으로 부르지는 않는다. 용인시 API와 용인시청 시설현황을 사람이 맞춰 본 CSV를 관리자 API(ADMIN-01)로 적재하고, 사용자 요청 중에는 DB 값만 쓴다.

## 3. 서비스에서 쓰이는 흐름 (RES-01·RES-02)

1. 보호자가 단기·장기, 필요한 날짜, 지역을 고른다. 지역을 비우면 대상자 등록 지역을 쓴다.
2. 기간과 대상자 나이(출생연도로 계산)에 맞는 제도를 Java 규칙으로 고른다. LLM은 쓰지 않는다.
3. 고른 제도에 연결된 유형의 시설을 검색 지역 구부터, 다음 다른 구 순서로 보여준다.
4. 추천 이유는 템플릿 문장이다. 시설은 "기흥구에 있는 주간이용센터예요.", 제도는 "장기 돌봄과 관련된 제도예요."처럼 나온다.
5. 모든 결과에 "실제 신청 자격과 이용 가능 여부는 해당 기관에 확인이 필요합니다."를 붙인다.

코드는 `ResourceService.search`(`src/main/java/com/batong/resource/service/ResourceService.java:49`)다.

## 6. 기획안에 추가할 내용 (제안)

기획안 수정은 기획 담당이 정한다. 아래는 넣을 문장의 초안이다.

1. **데이터 출처를 이름으로 적는다.** 기획안 3장은 "용인시 공공데이터"라고만 되어 있다. 2-1의 두 원자료와 2-2의 사업안내 문서명을 적는다.
2. **정리 방식을 적는다.** "용인시 API에는 시설 유형이 없어 시청 시설현황과 맞춰 유형을 붙였다"는 과정 자체가 공공데이터를 실제 문제에 쓰는 사례다.
3. **데이터 품질 문제를 발견한 사실을 적는다.** 시드 CSV에서 6곳(`needs_check=Y`)은 API와 시청 자료의 이름·주소·전화가 서로 다르다. 공공데이터의 불일치를 서비스가 드러낼 수 있다는 점은 지자체 공급 모델의 근거가 된다.
4. **단기 공백의 현실을 적는다.** 용인에는 장애인 단기거주시설 공공데이터가 0건이다. 긴급돌봄이 필요할 때 시설이 아닌 제도와 신청처를 먼저 안내하는 이유가 된다.
5. **P1 목록에 5장 2~4번을 추가한다.**

- "공공데이터 API를 실시간 연동했다." 정리한 CSV를 적재한다.
- "경기데이터드림 데이터를 쓴다." 확인만 했고 용인 행이 없어 쓰지 않았다.
- "AI가 맞춤 기관을 추천한다." 추천은 규칙이고, AI 추천 이유(AI-04)는 P1이다.
- "신청 가능 여부까지 알려준다." 화면에 기관 확인이 필요하다고 표시한다.
- "용인 발달장애인 OO명." 원 통계를 확인하기 전에는 쓰지 않는다.
